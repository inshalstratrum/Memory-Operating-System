### System Architecture Specification: Phase 2 – Memory Schema and Semantic Routing

#### 1\. Deliverable 1: ChromaDB Metadata Schema and Chunking Strategy

##### 1.1 JSON Metadata Schema Definition

To ensure the integrity of the  **Memory OS v5 / Shali OS**  ecosystem, every vector entry generated by the SentenceTransformer ( **all-MiniLM-L6-v2** ) and stored within ChromaDB must adhere to a rigid metadata structure. This schema is engineered for high-concurrency retrieval on the localized  **RTX 2060 Super**  hardware, facilitating rapid semantic lookups while enforcing strict data governance.  
{  
  "type": "string",  
  "agent": "string",  
  "project\_id": "string",  
  "thread\_id": "string",  
  "timestamp": "ISO 8601",  
  "importance": "float",  
  "pillar": "string",  
  "security\_level": "integer",  
  "feedback\_score": "float"  
}

**Schema Field Specifications:**

* **type** : Categorizes the vector (e.g., user\_input, ai\_response, system\_action).  
* **agent** : Maps the entry to a specific specialized sub-agent (e.g., coding, medical, creative, client).  
* **project\_id** : The primary key for workspace isolation (e.g., "Violet", "Mahmoud").  
* **thread\_id** : Maintains chronological session integrity for the UI.  
* **timestamp** : ISO 8601 format, critical for temporal decay and the "Security Guard Protocol."  
* **importance** : A float (0.0–1.0) used to shield high-value data from time-based decay.  
* **pillar** : Canonical classification for routing (Deen, Vessel, Stewardship, or Web).  
* **feedback\_score** : Aggregated 👍/👎 value for retrieval ranking.

##### 1.2 Data Isolation and Silo Architecture

Based on the multi-tenant requirements of  **Memory OS v5 / Shali OS**  379, 1311, the system employs a "Collection-Level Separation" protocol to prevent context bleed.

* **Workspace Siloing** : Each project\_id (e.g., Client: Violet vs. Client: Mahmoud) triggers the creation of a discrete, isolated ChromaDB collection. This ensures that sensitive project guidelines or financial data from one workspace are physically unreachable by queries originating in another (Ref: E003255).  
* **The Master PIN Protocol** : For sensitive metadata (e.g., server passwords, private keys), the system enforces a  **Master PIN (7777)**  requirement. Even if a semantic match is found, the orchestrator.py blocks the retrieval of the content unless the 4-digit PIN is verified in the active session context (Ref: E003250).  
* **State Separation** : The system distinguishes between the projects.json UI state (chronological history) and the ChromaDB vector state (semantic conceptual memory), ensuring that deleting a chat thread does not inadvertently wipe the deep conceptual embeddings required for RAG (Ref: E003265).

##### 1.3 250-Word Stability Protocol

The text segmentation protocol for  **Shali OS**  is standardized to preserve the high-dimensional accuracy of the  **SentenceTransformer**  embeddings while staying within the efficient context limits of the  **Llama 3.1 8B**  model.**"250-Word Stability Protocol"**  As established in technical audits 1683, 1714, 250-word segments represent the "Goldilocks Zone" for vector density. Larger segments tend to dilute the specific intent of a user prompt, while smaller segments lose the structural context required for complex technical tasks like After Effects scripting or Python debugging.**Technical Justification:**  The protocol utilizes a 15% overlapping window (approx. 35-40 words) at each boundary. This overlap is critical for preserving transitional logic and cross-chunk references. By maintaining this overlap, the  **OpenRouter**  RAG pipeline avoids "semantic fragmentation," where a crucial instruction is split and rendered unretrievable. This is especially vital for maintaining the "Science of Motion Graphics" mastery required for specialized creative tasks (Ref: E002653, E002908).

#### 2\. Deliverable 2: Langflow Semantic Routing and Temporal Filtering

##### 2.2 Temporal Filtering and Memory State Logic

Memory state logic in  **Shali OS**  utilizes a multi-layered approach to simulate persistent cognition.

1. **Active Memory** : Real-time context derived from the current thread\_id. This is "Thread-Aware" memory that prioritizes the immediate conversation flow stored in projects.json.  
2. **Historical Memory** : Persistent long-term data retrieved via semantic similarity across the specific pillar and project\_id. This layer now utilizes  **Global Memory Search**  to pull from both the specific agent silo and the "General" silo to prevent "Silo Amnesia" (Ref: E003242).  
3. **Task/Deferred Memory** : State-based memory for pending automation routines or system-level updates executed via automation.py.**Time Decay and Feedback Scoring:**  The system applies a "Time Decay" score 353 to penalize older interactions. However, this is now influenced by the  **Feedback System**  (Ref: E003267). Data with positive 👍 votes receives a "relevance boost," effectively halting the decay of highly useful historical context. Conversely, 👎 votes accelerate decay, ensuring the system "forgets" incorrect or hallucinated responses over time.

##### 2.3 Provenance and Studio Directives

Per the STUDIO DIRECTIVE,  **Memory OS v5**  enforces a strict  **Auditability**  protocol. Every retrieved memory chunk must be appended with its source project\_id and timestamp in the status\_display sidebar of the PyQt5 interface. This ensures the system is always  **Grounding**  its responses in verified data rather than model hallucinations. To prevent DLL collisions on Windows environments, the system must follow the  **PyTorch-First Loading**  protocol (importing torch prior to PyQt5) to maintain architectural stability and avoid the  **c10.dll**  crash. All sensitive data retrieval is gated by the  **Master PIN (7777)** , ensuring that provenance tracking and security are inseparable components of the canonical memory state.
